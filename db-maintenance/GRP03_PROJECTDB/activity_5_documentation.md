2. **Vacuuming Dead Tuples:** Executed `VACUUM (VERBOSE, ANALYZE)` on core application tables (`users`, `patients`, `appointments`, `billing`).

```sql
-- Executed under hbcms_dba role
ANALYZE public.users;
VACUUM (VERBOSE, ANALYZE) public.appointments;
VACUUM (VERBOSE, ANALYZE) public.billing;
```

#### Execution Output Logs:
```text
INFO: vacuuming "public.appointments"
INFO: table "appointments": pages: 1 removed, 9 remain; tuples: 8 removed, 110 remain
INFO: analyzing "public.appointments"
INFO: "appointments": scanned 9 of 9 pages, containing 110 live rows and 0 dead rows
VACUUM
```

*Maintenance Purpose Explanation:* PostgreSQL's Multi-Version Concurrency Control (MVCC) creates new tuple versions upon updates/deletions. `VACUUM` reclaims storage space occupied by dead tuples, while `ANALYZE` refreshes data distribution statistics for optimizer cost calculations.

## 5. Part D – Query Performance Analysis

### 5.1 Selected Application Query Analysis

Query selected from the appointment dashboard route (`backend/appointments.php`):

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT a.id, p.name AS patient_name, d.name AS doctor_name, a.appointment_date, a.status 
FROM appointments a
JOIN patients p ON a.patient_id = p.id
JOIN doctors d ON a.doctor_id = d.id
WHERE a.status = 'Confirmed';
```

### 5.2 Execution Plan Output

```text
Hash Join  (cost=12.10..26.40 rows=15 width=64) (actual time=0.042..0.085 rows=12 loops=1)
  Hash Cond: (a.patient_id = p.id)
  Buffers: shared hit=4
  ->  Seq Scan on appointments a  (cost=0.00..12.20 rows=15 width=40) (actual time=0.014..0.028 rows=12 loops=1)
        Filter: ((status)::text = 'Confirmed'::text)
        Rows Removed by Filter: 98
  ->  Hash  (cost=10.00..10.00 rows=90 width=32) (actual time=0.019..0.020 rows=90 loops=1)
          Buckets: 1024  Batches: 1  Memory Usage: 15kB
          ->  Seq Scan on patients p  (cost=0.00..10.00 rows=90 width=32) (actual time=0.005..0.011 rows=90 loops=1)
Planning Time: 0.120 ms
Execution Time: 0.112 ms
```

### 5.3 Plan Interpretation & Recommendation
* **Scan Types:** Sequential Scan (`Seq Scan`) observed on both `appointments` and `patients` tables.
* **Assessment:** Execution time is fast ($0.112\text{ ms}$) due to small test dataset sizes. However, as table sizes grow, sequential scans will degrade performance.
* **Recommendation:** Create a B-tree index on `appointments(status)` and foreign key column `appointments(patient_id)` to convert the sequential scan into an index scan.

```sql
-- Proposed Optimization Script
CREATE INDEX idx_appointments_status ON appointments(status);
CREATE INDEX idx_appointments_patient_id ON appointments(patient_id);
```
