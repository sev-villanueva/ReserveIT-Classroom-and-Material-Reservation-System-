## 4. Part C – Routine Maintenance Execution

### 4.1 Maintenance Operations Performed

1. **Refreshing Planner Statistics:** Executed `ANALYZE` across all public tables to update the `pg_statistic` system catalog.
2. **Vacuuming Dead Tuples:** Executed `VACUUM (VERBOSE, ANALYZE)` on core application tables (`members`, `trainers`, `memberships`, `payments`, `attendance`, `classes`).

```sql
-- Executed under dba_admin role
ANALYZE public.members;
ANALYZE public.memberships;
VACUUM (VERBOSE, ANALYZE) public.attendance;
VACUUM (VERBOSE, ANALYZE) public.payments;
```

#### Execution Output Logs:
```text
INFO: vacuuming "public.attendance"
INFO: table "attendance": pages: 1 removed, 8 remain; tuples: 5 removed, 95 remain
INFO: analyzing "public.attendance"
INFO: "attendance": scanned 8 of 8 pages, containing 95 live rows and 0 dead rows
VACUUM
```

*Maintenance Purpose Explanation:* PostgreSQL's Multi-Version Concurrency Control (MVCC) creates new tuple versions upon updates/deletions. `VACUUM` reclaims storage space occupied by dead tuples, while `ANALYZE` refreshes data distribution statistics for optimizer cost calculations.

## 5. Part D – Query Performance Analysis

### 5.1 Selected Application Query Analysis
Query selected from membership renewal and active profile check (`src/main/java/com/batumbakal/gym/service/MembershipService.java`):

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT m.member_id, m.first_name, m.last_name, ms.status, pl.plan_name
FROM members m
JOIN memberships ms ON m.member_id = ms.member_id
JOIN membership_plans pl ON ms.plan_id = pl.plan_id
WHERE ms.status = 'Active';
```

### 5.2 Execution Plan Output
```text
Hash Join  (cost=14.20..28.60 rows=12 width=72) (actual time=0.040..0.082 rows=10 loops=1)
  Hash Cond: (ms.plan_id = pl.plan_id)
  ->  Hash Join  (cost=11.10..25.30 rows=12 width=56) (actual time=0.030..0.065 rows=10 loops=1)
        Hash Cond: (m.member_id = ms.member_id)
        ->  Seq Scan on members m  (cost=0.00..11.50 rows=50 width=36) (actual time=0.005..0.015 rows=50 loops=1)
        ->  Hash  (cost=10.95..10.95 rows=12 width=32) (actual time=0.020..0.021 rows=10 loops=1)
              Buckets: 1024  Batches: 1  Memory Usage: 9kB
              ->  Seq Scan on memberships ms  (cost=0.00..10.95 rows=12 width=24) (actual time=0.010..0.016 rows=10 loops=1)
                    Filter: ((status)::text = 'Active'::text)
                    Rows Removed by Filter: 2
  ->  Hash  (cost=2.30..2.30 rows=3 width=32) (actual time=0.005..0.006 rows=3 loops=1)
        Buckets: 1024  Batches: 1  Memory Usage: 9kB
        ->  Seq Scan on membership_plans pl  (cost=0.00..2.30 rows=3 width=32) (actual time=0.002..0.003 rows=3 loops=1)
Planning Time: 0.145 ms
Execution Time: 0.110 ms
```

### 5.3 Plan Interpretation & Recommendation
* **Scan Types:** Sequential Scan (`Seq Scan`) observed on `memberships` and `members` tables.
* **Assessment:** Execution time is extremely fast ($0.110\text{ ms}$) due to the current small development dataset size. However, as gym member records scale, sequential scans will degrade query performance.
* **Recommendation:** Create targeted indexes on `memberships(status)`, `memberships(member_id)`, and `memberships(plan_id)` to optimize join performance.

```sql
-- Proposed Optimization Script
CREATE INDEX IF NOT EXISTS idx_memberships_status ON memberships(status);
CREATE INDEX IF NOT EXISTS idx_memberships_member_id ON memberships(member_id);
CREATE INDEX IF NOT EXISTS idx_memberships_plan_id ON memberships(plan_id);
```
