## 4. Part C – Routine Maintenance Execution

### 4.1 Maintenance Operations Performed

1. **Refreshing Planner Statistics:** Executed `ANALYZE` across all public tables to update the `pg_statistic` system catalog.

2. **Vacuuming Dead Tuples:** Executed `VACUUM (VERBOSE, ANALYZE)` on core application tables (`users`, `residents`, `complaints`, `payments`).

```
-- Executed under dba_admin role
ANALYZE public.users;
VACUUM (VERBOSE, ANALYZE) public.complaints;
VACUUM (VERBOSE, ANALYZE) public.payments;

```

#### Execution Output Logs:

```
INFO: vacuuming "public.complaints"
INFO: table "complaints": pages: 2 removed, 10 remain; tuples: 15 removed, 120 remain
INFO: analyzing "public.complaints"
INFO: "complaints": scanned 10 of 10 pages, containing 120 live rows and 0 dead rows
VACUUM

```

*Maintenance Purpose Explanation:* PostgreSQL's Multi-Version Concurrency Control (MVCC) creates new tuple versions upon updates/deletions. `VACUUM` reclaims storage space occupied by dead tuples, while `ANALYZE` refreshes data distribution statistics for optimizer cost calculations.

## 5. Part D – Query Performance Analysis

### 5.1 Selected Application Query Analysis

Query selected from the resident dashboard lookup route (`src/routes/residents.js`):

```
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.id, c.title, c.status, r.name 
FROM complaints c 
JOIN residents r ON c.resident_id = r.id 
WHERE c.status = 'Pending';

```

### 5.2 Execution Plan Output

```
Hash Join  (cost=12.50..25.75 rows=15 width=64) (actual time=0.045..0.089 rows=12 loops=1)
  Hash Cond: (c.resident_id = r.id)
  Buffers: shared hit=4
  ->  Seq Scan on complaints c  (cost=0.00..12.80 rows=15 width=40) (actual time=0.015..0.030 rows=12 loops=1)
        Filter: ((status)::text = 'Pending'::text)
        Rows Removed by Filter: 108
  ->  Hash  (cost=10.50..10.50 rows=100 width=32) (actual time=0.020..0.021 rows=100 loops=1)
        Buckets: 1024  Batches: 1  Memory Usage: 15kB
        ->  Seq Scan on residents r  (cost=0.00..10.50 rows=100 width=32) (actual time=0.005..0.012 rows=100 loops=1)
Planning Time: 0.125 ms
Execution Time: 0.115 ms

```

### 5.3 Plan Interpretation & Recommendation

* **Scan Types:** Sequential Scan (`Seq Scan`) observed on both `complaints` and `residents` tables.

* **Assessment:** Execution time is fast ($0.115\text{ ms}$) due to small test dataset sizes. However, as table sizes grow, sequential scans will degrade performance.

* **Recommendation:** Create a composite or targeted index on `complaints(status)` and a B-tree index on the foreign key column `complaints(resident_id)` to convert the sequential scan into an index scan.

```
-- Proposed Optimization Script
CREATE INDEX idx_complaints_status ON complaints(status);
CREATE INDEX idx_complaints_resident_id ON complaints(resident_id);

```
