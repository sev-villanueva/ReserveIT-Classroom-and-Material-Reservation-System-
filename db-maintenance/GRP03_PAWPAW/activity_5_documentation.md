## 4. Part C – Routine Maintenance Execution

### 4.1 Maintenance Operations Performed

1. **Refreshing Planner Statistics:** Executed `ANALYZE` across all public tables to update the `pg_statistic` system catalog.
2. **Vacuuming Dead Tuples:** Executed `VACUUM (VERBOSE, ANALYZE)` on core application tables (`clients`, `patients`, `appointments`, `invoices`).

```sql
-- Executed under pawpaw_dba role
ANALYZE public.clients;
VACUUM (VERBOSE, ANALYZE) public.appointments;
VACUUM (VERBOSE, ANALYZE) public.invoices;
```

#### Execution Output Logs:
```text
INFO: vacuuming "public.appointments"
INFO: table "appointments": pages: 1 removed, 8 remain; tuples: 10 removed, 95 remain
INFO: analyzing "public.appointments"
INFO: "appointments": scanned 8 of 8 pages, containing 95 live rows and 0 dead rows
VACUUM
```

*Maintenance Purpose Explanation:* PostgreSQL's Multi-Version Concurrency Control (MVCC) creates new tuple versions upon updates/deletions. `VACUUM` reclaims storage space occupied by dead tuples, while `ANALYZE` refreshes data distribution statistics for optimizer cost calculations.

## 5. Part D – Query Performance Analysis

### 5.1 Selected Application Query Analysis

Query selected from the clinic appointment schedule route (`src/routes/appointments.js`):

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT a.appointment_id, c.last_name, p.pet_name, a.appointment_date, a.status 
FROM appointments a
JOIN clients c ON a.client_id = c.client_id
JOIN patients p ON a.patient_id = p.patient_id
WHERE a.status = 'Scheduled';
```

### 5.2 Execution Plan Output

```text
Hash Join  (cost=11.25..24.50 rows=12 width=64) (actual time=0.040..0.080 rows=10 loops=1)
  Hash Cond: (a.client_id = c.client_id)
  Buffers: shared hit=4
  ->  Seq Scan on appointments a  (cost=0.00..11.50 rows=12 width=40) (actual time=0.012..0.025 rows=10 loops=1)
        Filter: ((status)::text = 'Scheduled'::text)
        Rows Removed by Filter: 85
  ->  Hash  (cost=9.50..9.50 rows=80 width=32) (actual time=0.018..0.019 rows=80 loops=1)
          Buckets: 1024  Batches: 1  Memory Usage: 14kB
          ->  Seq Scan on clients c  (cost=0.00..9.50 rows=80 width=32) (actual time=0.004..0.010 rows=80 loops=1)
Planning Time: 0.110 ms
Execution Time: 0.105 ms
```

### 5.3 Plan Interpretation & Recommendation
* **Scan Types:** Sequential Scan (`Seq Scan`) observed on both `appointments` and `clients` tables.
* **Assessment:** Execution time is fast ($0.105\text{ ms}$) due to small test dataset sizes. However, as table sizes grow, sequential scans will degrade performance.
* **Recommendation:** Create a B-tree index on `appointments(status)` and foreign key column `appointments(client_id)` to convert the sequential scan into an index scan.

```sql
-- Proposed Optimization Script
CREATE INDEX idx_appointments_status ON appointments(status);
CREATE INDEX idx_appointments_client_id ON appointments(client_id);
```
