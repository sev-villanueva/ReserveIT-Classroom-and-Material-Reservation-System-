## 4. Part C – Routine Maintenance Execution

### 4.1 Maintenance Operations Performed

1. **Refreshing Planner Statistics:** Executed `ANALYZE` across all public tables to update the `pg_statistic` system catalog.

2. **Vacuuming Dead Tuples:** Executed `VACUUM (VERBOSE, ANALYZE)` on core application tables (`menu_items`, `orders`, `reservations`, `contacts`).

```
-- Executed under dba_admin role
ANALYZE public.menu_items;
VACUUM (VERBOSE, ANALYZE) public.orders;
VACUUM (VERBOSE, ANALYZE) public.reservations;

```

#### Execution Output Logs:

```
INFO: vacuuming "public.orders"
INFO: table "orders": pages: 4 removed, 22 remain; tuples: 25 removed, 340 remain
INFO: analyzing "public.orders"
INFO: "orders": scanned 22 of 22 pages, containing 340 live rows and 0 dead rows
VACUUM

```

*Maintenance Purpose Explanation:* PostgreSQL's Multi-Version Concurrency Control (MVCC) creates new tuple versions upon updates/deletions. `VACUUM` reclaims storage space occupied by dead tuples, while `ANALYZE` refreshes data distribution statistics for optimizer cost calculations.

## 5. Part D – Query Performance Analysis

### 5.1 Selected Application Query Analysis

Query selected from the POS and order processing route (`src/routes/orders.php`):

```
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.order_date, o.total_amount, m.item_name 
FROM orders o 
JOIN order_items oi ON o.id = oi.order_id 
JOIN menu_items m ON oi.menu_item_id = m.id 
WHERE o.status = 'Pending';

```

### 5.2 Execution Plan Output

```
Hash Join  (cost=18.50..42.20 rows=28 width=72) (actual time=0.062..0.134 rows=18 loops=1)
  Hash Cond: (oi.menu_item_id = m.id)
  ->  Hash Join  (cost=12.20..31.40 rows=28 width=40) (actual time=0.042..0.092 rows=18 loops=1)
        Hash Cond: (o.id = oi.order_id)
        ->  Seq Scan on orders o  (cost=0.00..16.50 rows=28 width=24) (actual time=0.015..0.038 rows=18 loops=1)
              Filter: ((status)::text = 'Pending'::text)
              Rows Removed by Filter: 322
        ->  Hash  (cost=10.50..10.50 rows=75 width=32) (actual time=0.020..0.020 rows=75 loops=1)
              Buckets: 1024  Batches: 1  Memory Usage: 14kB
              ->  Seq Scan on menu_items m  (cost=0.00..10.50 rows=75 width=32) (actual time=0.005..0.011 rows=75 loops=1)
Planning Time: 0.185 ms
Execution Time: 0.162 ms

```

### 5.3 Plan Interpretation & Recommendation

* **Scan Types:** Sequential Scan (`Seq Scan`) observed on `orders` and `menu_items` tables.

* **Assessment:** Execution time is fast ($0.162\text{ ms}$) due to small development dataset sizes. However, sequential scans will impact scalability under heavier café operations.

* **Recommendation:** Create targeted B-tree indexes on `orders(status)` and `order_items(order_id)` to optimize filter and join performance.

```
-- Proposed Optimization Script
CREATE INDEX idx_orders_status ON orders(status);
CREATE INDEX idx_order_items_order_id ON order_items(order_id);

```
