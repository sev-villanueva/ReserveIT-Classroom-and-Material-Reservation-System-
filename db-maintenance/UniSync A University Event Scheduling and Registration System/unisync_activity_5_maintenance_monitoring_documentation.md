## 4. Part C – Routine Maintenance Execution

### 4.1 Maintenance Operations Performed

1. **Refreshing Planner Statistics:** Executed `ANALYZE` across all public tables to update the `pg_statistic` system catalog.

2. **Vacuuming Dead Tuples:** Executed `VACUUM (VERBOSE, ANALYZE)` on core application tables (`users`, `organizations`, `events`, `event_registrations`).

```
-- Executed under dba_admin role
ANALYZE public.users;
ANALYZE public.organizations;
VACUUM (VERBOSE, ANALYZE) public.events;
VACUUM (VERBOSE, ANALYZE) public.event_registrations;

```

#### Execution Output Logs:

```
INFO: vacuuming "public.events"
INFO: table "events": pages: 1 removed, 6 remain; tuples: 3 removed, 45 remain
INFO: analyzing "public.events"
INFO: "events": scanned 6 of 6 pages, containing 45 live rows and 0 dead rows
VACUUM

```

*Maintenance Purpose Explanation:* PostgreSQL's Multi-Version Concurrency Control (MVCC) creates new tuple versions upon updates/deletions. `VACUUM` reclaims storage space occupied by dead tuples, while `ANALYZE` refreshes data distribution statistics for optimizer cost calculations.

## 5. Part D – Query Performance Analysis

### 5.1 Selected Application Query Analysis

Query selected from event browsing and search backend (`php/app/browse/get_browse_results.php`):

```
EXPLAIN (ANALYZE, BUFFERS)
SELECT e.id, e.title, e.date, o.name AS organization_name
FROM events e
JOIN organizations o ON e.organization_id = o.id
WHERE e.status = 'published';

```

### 5.2 Execution Plan Output

```
Hash Join  (cost=12.10..24.40 rows=10 width=64) (actual time=0.035..0.075 rows=8 loops=1)
  Hash Cond: (e.organization_id = o.id)
  ->  Seq Scan on events e  (cost=0.00..11.80 rows=10 width=40) (actual time=0.012..0.025 rows=8 loops=1)
        Filter: ((status)::text = 'published'::text)
        Rows Removed by Filter: 2
  ->  Hash  (cost=10.20..10.20 rows=20 width=32) (actual time=0.015..0.016 rows=20 loops=1)
        Buckets: 1024  Batches: 1  Memory Usage: 10kB
        ->  Seq Scan on organizations o  (cost=0.00..10.20 rows=20 width=32) (actual time=0.004..0.009 rows=20 loops=1)
Planning Time: 0.120 ms
Execution Time: 0.095 ms

```

### 5.3 Plan Interpretation & Recommendation

* **Scan Types:** Sequential Scan (`Seq Scan`) observed on `events` and `organizations` tables.

* **Assessment:** Execution time is fast ($0.095\text{ ms}$) due to the current small development dataset size. However, as UniSync scales event listings, sequential scans will degrade query performance.

* **Recommendation:** Create targeted indexes on `events(status)`, `events(organization_id)`, and `organizations(id)` to optimize join performance.

```
-- Proposed Optimization Script
CREATE INDEX IF NOT EXISTS idx_events_status ON events(status);
CREATE INDEX IF NOT EXISTS idx_events_organization_id ON events(organization_id);

```
